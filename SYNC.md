# Синхронизация установок Codex

Синхронизация переносит проверенные общие правила между установками, не затирая локальные и проектные настройки.

## Главный принцип

> При неоднозначном конфликте сохранить локальную настройку, ничего не затирать и запросить решение пользователя.

Получение новой версии репозитория не означает автоматического принятия её правил.

## Локальная структура

Каноническое ядро берётся из `AGENTS_CORE.md`. Глобальный `~/.codex/AGENTS.md` разделяется на два блока:

```markdown
<!-- BEGIN BEST-PRACTICE MANAGED CORE -->
Синхронизируемые общие правила
<!-- END BEST-PRACTICE MANAGED CORE -->

<!-- BEGIN LOCAL OVERRIDES -->
Уведомления, пути, плагины, разрешения и другие настройки этой установки
<!-- END LOCAL OVERRIDES -->
```

Синхронизация может изменять только managed-блок. `LOCAL OVERRIDES` автоматически не редактируется.

## Состояние установки

Файл `~/.codex/best-practice-state.json` хранит только сведения о синхронизации:

```json
{
  "installed_version": "2.0.0",
  "installed_commit": "0123456789abcdef0123456789abcdef01234567",
  "synced_at": "2026-08-14T09:00:00Z",
  "local_profile": "workstation-2"
}
```

Секреты, токены, пути с учётными данными и содержимое локальных настроек в state-файл не записываются.

## Первичная интеграция

1. Получить `best-practice` в доступный этой установке каталог.
2. Прочитать `AGENTS_CORE.md`, `memory/VALIDITY.md` и текущий локальный `~/.codex/AGENTS.md`.
3. Отделить существующие универсальные правила от локальных настроек.
4. Сформировать предлагаемый managed-блок и `LOCAL OVERRIDES`.
5. Показать пользователю diff до записи.
6. При неоднозначности сохранить локальное значение и запросить решение.
7. Создать резервную копию локального `AGENTS.md`.
8. После подтверждения записать оба блока и проверить маркеры.
9. Только после успешной записи создать state-файл.

## Регулярная синхронизация

Последовательность всегда одинакова:

```text
fetch → diff → classify → review → managed AGENTS integration
      → usage profile compatibility check → config diff → approval
      → config integration → verification → report
```

1. Выполнить `git fetch` и определить целевую версию, не меняя локальные инструкции.
2. Прочитать state-файл и определить установленный commit.
3. Построить diff от установленного commit до целевого.
4. Прочитать относящиеся к диапазону записи `CHANGELOG.md` и изменённые релевантные файлы.
5. Классифицировать изменения по `memory/VALIDITY.md`:
   - безопасно применить;
   - сохранить локальное;
   - требуется решение.
6. Показать план интеграции до записи файлов.
7. После подтверждения создать резервную копию и изменить только managed-блок.
8. Проверить итоговый diff, границы блоков и сохранность `LOCAL OVERRIDES`.
9. Обновить state-файл только после успешной проверки.
10. Выдать отчёт.

## Синхронизация профиля использования

Интеграция managed-блока `AGENTS.md` и интеграция профиля использования
требуют независимое подтверждение. Не заменять `config.toml` целиком.

Профиль `config/USAGE_PROFILE.toml` задаёт только рекомендуемые общие
значения. Он не отменяет более конкретные проектные правила и не разрешает
перенос локальных MCP, плагинов, permissions, paths, projects или других
машинных настроек.

1. Проверить версию Codex и поддержку каждой модели и каждого ключа.
2. Если модель или ключ не поддерживается, ничего не записывать и запросить решение.
3. Сравнивать только шесть ключей из `config/USAGE_PROFILE.toml`:
   - `model`;
   - `model_reasoning_effort`;
   - `service_tier`;
   - `agents.max_concurrent_threads_per_session`;
   - `agents.default_subagent_model`;
   - `agents.default_subagent_reasoning_effort`.
4. Сохранить SHA-256 локального `config.toml` вместе с предлагаемым diff.
5. Перед записью пересчитать SHA-256; при изменении остановиться и построить diff заново.
6. Сохранить все остальные таблицы, ключи, комментарии и порядок локального файла.
7. Создать резервную копию, применить подтверждённые ключи и проверить загрузку.
8. При ошибке восстановить резервную копию и не обновлять state-файл.

Принятие managed-блока не означает принятия конфигурационного профиля, и
наоборот. Несовместимое или отклонённое значение остаётся локальным и
перечисляется в отчёте.

## Политика конфликтов

- `shared + enforce-shared`: предложить единое правило всем установкам; существующее противоречие показать до изменения.
- `local-default + preserve-local`: сохранить существующее локальное значение.
- `project`: не переносить в глобальное ядро.
- `ask`: не менять до решения пользователя.
- Отсутствующие, неизвестные или противоречивые метки трактовать как `ask`.
- Удаление или ослабление обязательного общего правила требует явного подтверждения.

## Отчёт

После синхронизации сообщить:

- предыдущую и новую версии;
- предыдущий и новый commit;
- принятые общие правила;
- сохранённые локальные настройки;
- конфликты и принятые решения;
- отложенные рекомендации;
- сведения, требующие актуальной проверки;
- изменённые локальные файлы.
- поддерживается ли рекомендуемый профиль текущей версией Codex;
- прежние и новые значения шести управляемых ключей;
- сохранённые локальные таблицы и настройки;
- несовместимые, отклонённые или отложенные значения;
- результат проверки модели, reasoning, service tier и ограничения агентов.

## Ошибки и восстановление

- GitHub недоступен: ничего не менять локально и сообщить об ошибке.
- State-файл отсутствует или содержит неизвестный commit: выполнить первичную интеграцию или полное сравнение.
- Managed-маркеры отсутствуют, повторяются или перепутаны: остановить запись и предложить восстановление структуры.
- Локальный файл изменился после построения плана: отменить запись и построить diff заново.
- Версия Codex, модель или ключ профиля не поддерживается: не изменять `config.toml`, сохранить локальные значения и запросить решение.
- SHA-256 `config.toml` изменился после показа diff: отменить запись и построить новый diff.
- Ошибка записи или проверки: восстановить managed-блок из резервной копии и не обновлять state-файл.
- Повторная синхронизация уже установленной версии: не менять файлы, сообщить об отсутствии новых изменений.

## Команда для другой установки

```text
Синхронизируй эту установку с https://github.com/pavel-tsapyuk/best-practice по процедуре SYNC.md. Сначала выполни fetch и построй diff от commit из ~/.codex/best-practice-state.json. Не меняй файлы до показа плана интеграции. Обновляй только блок BEST-PRACTICE MANAGED CORE, сохраняй LOCAL OVERRIDES, а при любом неоднозначном конфликте ничего не затирай и запроси моё решение. После подтверждённой интеграции проверь результат, обнови state-файл и выдай полный отчёт.
```

# Codex Best Practice

Версионируемый источник общих правил, принципов, инструментов и практических паттернов для нескольких установок Codex.

## Архитектура

Репозиторий не является файлом, который нужно целиком загружать в контекст каждой задачи.

- `AGENTS.md` — правила сопровождения самого репозитория.
- `AGENTS_CORE.md` — короткое каноническое ядро для синхронизируемой части глобального `~/.codex/AGENTS.md`.
- `SYNC.md` — безопасная интеграция обновлений на других машинах.
- `CHANGELOG.md` — существенные изменения правил и ожидаемого поведения.
- `VERSION` — текущая версия общей базы.
- `memory/VALIDITY.md` — словарь областей действия, стабильности и конфликтов.
- `memory/SOURCES.md` — реестр регулярно просматриваемых источников и правила отбора находок.
- `memory/` — подробная справочная база, читаемая по релевантности.

## Что одинаково на всех установках

В общее ядро входят универсальные правила:

- перед нетривиальной задачей проверить релевантные skills/superpowers;
- определить результат, criteria of done и границы;
- выбирать минимальную достаточную сложность;
- не использовать LLM вместо надёжной детерминированной логики;
- проверять изменчивые сведения и итоговый результат;
- читать только релевантные материалы из `memory/`;
- не принимать обновления правил автоматически.

## Что остаётся локальным

Установки могут различаться по уведомлениям, путям, ОС, оборудованию, плагинам, MCP, разрешениям и автоматизациям. Эти значения хранятся в `LOCAL OVERRIDES` и не затираются общими настройками.

Проектные правила остаются в проектных `AGENTS.md` и не переносятся в глобальное ядро.

## Модель работы

Одна основная машина раз в месяц собирает и проверяет полезные материалы, обновляет репозиторий, changelog и версию. Публикация существенных изменений выполняется после просмотра diff.

Другие установки работают по процедуре:

```text
fetch → diff → classify → review → integration → report
```

При неоднозначном конфликте локальное значение сохраняется, ничего не затирается, а решение запрашивается у пользователя.

## Подключение новой установки

1. Клонируй репозиторий в постоянный доступный каталог.
2. Попроси Codex выполнить первичную интеграцию по `SYNC.md`.
3. Проверь предлагаемый diff глобального `~/.codex/AGENTS.md`.
4. После подтверждения Codex создаст управляемый блок, сохранит локальные настройки и запишет `~/.codex/best-practice-state.json`.

## Команда синхронизации

Передай установке Codex:

```text
Синхронизируй эту установку с https://github.com/pavel-tsapyuk/best-practice по процедуре SYNC.md. Сначала выполни fetch и построй diff от commit из ~/.codex/best-practice-state.json. Не меняй файлы до показа плана интеграции. Обновляй только блок BEST-PRACTICE MANAGED CORE, сохраняй LOCAL OVERRIDES, а при любом неоднозначном конфликте ничего не затирай и запроси моё решение. После подтверждённой интеграции проверь результат, обнови state-файл и выдай полный отчёт.
```

## Чтение памяти

Codex не должен читать весь каталог `memory/` по умолчанию. Он выбирает материалы по задаче:

- разработка и проверка процесса — `SUPERPOWERS.md`, `PRINCIPLES.md`, `PATTERNS.md`;
- выбор инструмента — релевантные разделы `TOOLS.md` с обязательной актуальной проверкой;
- Bitrix24 и другие предметные сценарии — подходящие разделы `PROJECT_APPLICATIONS.md`;
- интерпретация меток — `VALIDITY.md`.
- обновление базы по внешним материалам — `SOURCES.md`, затем только релевантные тематические файлы.

Инструкция по установке приватного виджета лимита на компьютеры владельца: [CodexMeter](memory/PROJECT_APPLICATIONS.md#codexmeter).

Инструмент из радара — кандидат для оценки, а не обязательная зависимость или автоматическая рекомендация.

## Безопасность обновлений

- Новая запись в Git не становится активным правилом сама по себе.
- Managed-блок меняется только после анализа и показа плана.
- `LOCAL OVERRIDES` не редактируется автоматически.
- State-файл не содержит секретов.
- Изменчивые утверждения проверяются по первичным источникам перед применением.
- История v1 сохраняется в Git.

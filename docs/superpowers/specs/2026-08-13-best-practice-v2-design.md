# Best Practice v2: архитектура общей памяти Codex

## Цель

Перестроить `best-practice` из монолитного набора инструкций в управляемую базу общих правил для нескольких параллельных установок Codex.

Репозиторий остаётся единым версионируемым источником правды. При этом каждая установка сохраняет локальные настройки, а проектные репозитории — собственные инструкции. Обновление репозитория не означает автоматического принятия новых правил.

## Критерии готовности

Миграция v2 считается завершённой, когда:

1. Общее активное ядро отделено от справочной базы.
2. Корневой `AGENTS.md` описывает только сопровождение `best-practice`.
3. `AGENTS_CORE.md` помещается примерно на 1–2 страницы и содержит только универсальные правила.
4. Справочные материалы читаются по релевантности, а не целиком при каждой задаче.
5. Каждое изменчивое или контекстное правило можно классифицировать по области действия, стабильности и политике конфликта.
6. Существенные изменения описываются в `CHANGELOG.md`.
7. `SYNC.md` задаёт безопасный процесс обновления нескольких установок.
8. Неоднозначные конфликты сохраняют локальное значение и требуют решения пользователя.
9. Установка хранит принятую версию и commit общей базы без секретов.
10. v1 остаётся доступна в истории Git, а переход на v2 описан в changelog.

## Уровни конфигурации

Система разделяет инструкции по области ответственности:

1. Системные и платформенные ограничения — не управляются этим репозиторием и всегда сохраняют фактический приоритет среды.
2. Прямой запрос пользователя — применяется в пределах более высоких ограничений.
3. Проектный `AGENTS.md` — задаёт конкретные правила проекта.
4. Локальные настройки установки — описывают машину, окружение и предпочтения, которые не должны унифицироваться автоматически.
5. Общее ядро `best-practice` — универсальные правила работы для всех установок.
6. `memory/` — справочная база, применяемая только по релевантности.

В управляемой пользователем части проектные инструкции конкретнее глобального ядра, а локальные параметры окружения не заменяются общими рекомендациями без явного решения.

## Структура репозитория

```text
best-practice/
├── AGENTS.md
├── AGENTS_CORE.md
├── README.md
├── CHANGELOG.md
├── SYNC.md
├── VERSION
├── docs/
│   └── superpowers/specs/
└── memory/
    ├── VALIDITY.md
    ├── SUPERPOWERS.md
    ├── PRINCIPLES.md
    ├── TOOLS.md
    ├── PATTERNS.md
    └── PROJECT_APPLICATIONS.md
```

### `AGENTS.md`

Короткие правила сопровождения самого репозитория:

- сохранять разделение активного ядра и справочной базы;
- проверять изменчивые сведения по первичным источникам;
- маркировать область действия, стабильность и политику конфликта;
- обновлять changelog при существенном изменении поведения;
- не активировать новые правила автоматически;
- не хранить секреты.

Он не дублирует глобальное ядро.

### `AGENTS_CORE.md`

Канонический шаблон управляемого блока глобального `~/.codex/AGENTS.md`. В нём остаются только универсальные правила:

- перед нетривиальной задачей проверять доступные skills/superpowers и применять релевантные;
- определять наблюдаемый результат, criteria of done, границы и запрещённые изменения;
- выбирать минимальную достаточную сложность;
- не использовать LLM там, где достаточно детерминированной логики;
- читать только релевантные материалы из `memory/`;
- проверять изменчивые сведения;
- соблюдать проектные инструкции;
- проверять результат перед заявлением о завершении;
- не считать обновление базы автоматическим принятием новых правил.

Подробные объяснения и анти-паттерны остаются в `memory/`.

### `memory/`

Содержит полную базу знаний. Codex выбирает релевантные файлы и разделы по задаче. `memory/TOOLS.md` не является списком обязательных зависимостей.

### `VALIDITY.md`

Определяет словарь меток и правила их применения.

Область действия:

- `shared` — общее для всех установок;
- `local-default` — рекомендуемое значение, которое допускает локальное переопределение;
- `project` — применимо только в контексте конкретного проекта или класса проектов.

Стабильность:

- `stable` — фундаментальный принцип, редко требующий пересмотра;
- `verify-current` — сведения необходимо проверять перед применением;
- `project-specific` — достоверность и применимость зависят от проекта;
- `heuristic` — полезный ориентир, но не обязательное правило или SLA.

Политика конфликта:

- `enforce-shared` — обязательное общее правило; ослабление требует явного решения пользователя;
- `preserve-local` — локальное значение сохраняется;
- `ask` — ничего не менять до решения пользователя.

Метки можно задавать для раздела Markdown компактным блоком:

```yaml
scope: shared
stability: stable
conflict: enforce-shared
```

Не требуется маркировать каждое предложение. Одна метка может относиться к логически однородному разделу.

## Локальный глобальный файл

Глобальный `~/.codex/AGENTS.md` делится на управляемую и локальную части:

```markdown
<!-- BEGIN BEST-PRACTICE MANAGED CORE -->
Общие синхронизируемые правила
<!-- END BEST-PRACTICE MANAGED CORE -->

<!-- BEGIN LOCAL OVERRIDES -->
Локальные настройки этой установки
<!-- END LOCAL OVERRIDES -->
```

Синхронизация может изменять только управляемый блок. Локальный блок не редактируется автоматически.

К локальным настройкам относятся, например:

- наличие, отсутствие и тип уведомлений;
- пути и рабочие каталоги;
- особенности ОС и оборудования;
- установленные плагины, MCP и коннекторы;
- локальные разрешения;
- расписания автоматизаций;
- настройки конкретной машины.

## Состояние установки

Каждая установка хранит `~/.codex/best-practice-state.json`:

```json
{
  "installed_version": "2.0.0",
  "installed_commit": "0123456789abcdef0123456789abcdef01234567",
  "synced_at": "2026-08-13T18:00:00Z",
  "local_profile": "workstation-2"
}
```

Файл не содержит секретов. Он нужен для построения точного diff от последней принятой версии.

Если файла состояния нет, установка выполняет первичную интеграцию: анализирует текущее локальное ядро, формирует план слияния и создаёт state-файл только после подтверждённого применения.

## Процесс обновления источника правды

Одна основная машина раз в месяц:

1. Собирает новые материалы и предложения.
2. Проверяет изменчивые утверждения по первичным источникам.
3. Классифицирует каждое существенное изменение.
4. Обновляет справочные файлы и при необходимости предлагает изменение ядра.
5. Записывает изменение поведения в `CHANGELOG.md`.
6. Повышает семантическую версию.
7. Показывает пользователю diff, источники, риски и ожидаемое влияние.
8. Публикует изменения только после подтверждения пользователя.

Рекомендуемая семантика версий:

- `MAJOR` — несовместимое изменение ядра или политики синхронизации;
- `MINOR` — новое совместимое правило, раздел или существенная рекомендация;
- `PATCH` — уточнение без изменения ожидаемого поведения.

## Процесс синхронизации установок

На остальных машинах используется последовательность:

```text
fetch → diff → classify → review → integration → report
```

1. Получить актуальное состояние `best-practice` без немедленного изменения локальных инструкций.
2. Прочитать локальный state-файл.
3. Сравнить установленный commit с целевым.
4. Прочитать соответствующие записи `CHANGELOG.md` и изменённые релевантные файлы.
5. Классифицировать каждое изменение как:
   - безопасно применить;
   - сохранить локальное;
   - требуется решение пользователя.
6. Сформировать план слияния до записи файлов.
7. Сохранить локальное значение при любом неоднозначном конфликте.
8. После подтверждения изменить только управляемый блок глобального файла.
9. Проверить маркеры, итоговый diff и отсутствие повреждения локального блока.
10. Обновить state-файл.
11. Выдать отчёт.

## Политика конфликтов

Основное правило:

> При неоднозначном конфликте сохранить локальную настройку, ничего не затирать и запросить решение пользователя.

Дополнительные правила:

- `shared + enforce-shared` предлагается применить ко всем установкам; существующее противоречие показывается пользователю до изменения.
- `local-default + preserve-local` не заменяет существующее локальное значение.
- `project` не переносится в глобальное ядро.
- `ask` всегда требует решения.
- удаление или ослабление обязательного общего правила требует явного подтверждения.
- отсутствие технической возможности определить границы управляемого блока блокирует автоматическую запись, но не анализ и отчёт.

## Отчёт синхронизации

После каждого обновления установка сообщает:

- предыдущую и новую версии;
- предыдущий и новый commit;
- принятые общие правила;
- сохранённые локальные настройки;
- конфликты и решения;
- непринятые рекомендации;
- сведения, которые требуют актуальной проверки;
- изменённые локальные файлы.

## Ошибки и безопасное восстановление

- Недоступен GitHub: не менять локальные инструкции, сообщить об ошибке.
- Неизвестная установленная версия: выполнить полное сравнение, не применять изменения автоматически.
- Повреждены или отсутствуют маркеры: остановить запись и предложить восстановление структуры.
- Локальный файл изменился после построения плана: повторно построить diff.
- Конфликтующие метки: считать правило `ask` и сохранить локальное состояние.
- Ошибка записи: не обновлять state-файл.
- Частично выполненное обновление: восстановить предыдущий управляемый блок из локальной резервной копии и сообщить пользователю.

Перед изменением `~/.codex/AGENTS.md` создаётся локальная резервная копия. Срок и способ хранения могут определяться конкретной установкой.

## Проверка реализации

Нужны сценарии, подтверждающие:

1. Новая установка корректно создаёт управляемый блок без удаления существующих локальных правил.
2. Общее правило обновляется внутри управляемого блока.
3. Локальное уведомление не затирается общим значением.
4. Проектная рекомендация не попадает в глобальное ядро.
5. Неоднозначный конфликт не изменяет файл до решения пользователя.
6. Повреждённые маркеры останавливают запись.
7. State-файл обновляется только после успешной интеграции.
8. Повторная синхронизация той же версии не меняет файлы.
9. Отчёт перечисляет все принятые, сохранённые и отложенные изменения.
10. Секреты не попадают в репозиторий, state-файл или отчёт.

## Границы v2

В v2 входят структура репозитория, маркировка, документация синхронизации, короткое ядро, changelog и формат локального состояния.

В v2 не входят:

- фоновая синхронизация без команды пользователя;
- автоматическое принятие изменений ядра;
- централизованное управление секретами;
- принудительная унификация плагинов, путей и уведомлений;
- самостоятельная модификация проектных репозиториев;
- отдельная программа синхронизации, пока документированный workflow достаточен.

## Миграция с v1

1. Сохранить полную историю v1 в Git.
2. Перенести универсальные активные правила из текущего `AGENTS.md` в короткий `AGENTS_CORE.md`.
3. Переписать корневой `AGENTS.md` как инструкцию сопровождения репозитория.
4. Добавить `VALIDITY.md`, `SYNC.md` и `CHANGELOG.md`.
5. Разметить существующие материалы на уровне логических разделов.
6. Обновить README и VERSION до `2.0.0`.
7. Не изменять глобальные файлы других установок в рамках миграции репозитория; для них применяется отдельный процесс синхронизации.

# Единая политика оптимизации ChatGPT и Codex

**Дата:** 2026-09-24  
**Статус:** design approved in chat; written specification awaiting review  
**Область:** три личные установки Codex и общая учётная запись ChatGPT

## 1. Цель

Создать единую переносимую политику, которая перед каждой задачей оценивает достаточность выбранного инструмента, модели, reasoning effort, service tier и числа агентов, но не добавляет лишнюю церемонию и не увеличивает расход сама по себе.

Политика должна помочь владельцу стабильно завершать недельное окно общего лимита ChatGPT/Codex в целевом диапазоне 80–85%, не используя reset credits как штатный механизм.

## 2. Наблюдаемый результат

После внедрения на каждой установке:

1. Перед каждой задачей Codex выполняет короткий внутренний resource preflight.
2. Если текущая конфигурация подходит, Codex не комментирует preflight и сразу выполняет задачу.
3. Если инструмент, модель, reasoning, скорость или число агентов существенно избыточны, Codex до дорогой работы сообщает одну краткую рекомендацию с конкретной альтернативой.
4. Обычная работа запускается в standard/default service tier с одним агентом и low/medium reasoning.
5. Параллельная агентская работа ограничена двумя субагентами, а субагент по умолчанию использует экономичную модель.
6. Детерминированные операции по возможности выполняются обычным кодом, CLI, тестами или автоматизацией без LLM.
7. Общие правила одинаковы на трёх компьютерах, а локальные пути, уведомления, MCP, плагины, разрешения и особенности оборудования сохраняются.
8. Подробные и изменчивые сведения не загружаются в контекст каждой простой задачи.

## 3. Исходные наблюдения

Политика основана на отчётах трёх машин за май–сентябрь 2026 года.

- HP: 250 журналов и 2 086 пользовательских сообщений; большинство контекстов использовало GPT-5.6 Sol.
- PC: 50 основных задач, 173 субагента и 1 811 сообщений; 25 основных задач имели automation source.
- Redmi: 21 основная задача, 175 субагентов и 2 001 сообщение; 140 из 196 агентских записей использовали high/xhigh/ultra/max reasoning.
- На момент анализа использовано 68% недельного лимита; линейный прогноз при прежнем темпе составлял около 104%.
- Локальная история ChatGPT не позволяет надёжно распределить общий расход между ChatGPT и Codex.

Количественные данные используются как диагностические признаки, а не как точная атрибуция стоимости отдельным задачам.

## 4. Архитектура политики

Политика разделяется на четыре слоя.

### 4.1. Активное короткое ядро

`AGENTS_CORE.md` содержит только устойчивое обязательное поведение:

- молчаливый preflight перед задачей;
- минимальная достаточная сложность;
- standard/default speed, один агент и low/medium reasoning по умолчанию;
- предупреждение только при существенном несоответствии;
- явное обоснование high/xhigh/max/ultra, fast mode и субагентов;
- бюджет, STOP-условие и лимит итераций для долгой задачи;
- уважение к явно выбранному пользователем режиму.

Ядро использует роли моделей — лёгкая, рабочая, старшая — без привязки к текущим названиям. Это снижает риск устаревания активных правил.

### 4.2. Подробная справочная политика

Новый файл `memory/USAGE_OPTIMIZATION.md` содержит:

- классификацию задач D/S/M/L/C;
- текущую привязку классов к доступным моделям;
- правила выбора ChatGPT, Codex, CLI, коннектора, browser/computer use;
- правила reasoning и service tier;
- условия использования субагентов;
- правила управления контекстом и handoff между компьютерами;
- недельные бюджетные пороги;
- процедуру двухнедельного и последующего недельного аудита;
- дату актуализации и ссылки на официальную документацию OpenAI.

Файл получает смешанные metadata-разделы:

- устойчивые принципы: `scope: shared`, `stability: stable`, `conflict: enforce-shared`;
- числовые пороги и оценочные правила: `scope: shared`, `stability: heuristic`, `conflict: ask`;
- актуальные названия моделей и продуктовые сведения: `scope: local-default` или `shared`, `stability: verify-current`, `conflict: preserve-local` или `ask` в зависимости от раздела.

Этот файл читается только когда задача потенциально дорогая, требуется выбор режима, достигнут бюджетный порог или выполняется аудит. Простой запрос не должен загружать весь документ.

### 4.3. Канонический конфигурационный профиль

Новый файл `config/USAGE_PROFILE.toml` хранит рекомендуемые общие значения:

```toml
model = "gpt-6-sol"
model_reasoning_effort = "medium"
service_tier = "default"

[agents]
max_concurrent_threads_per_session = 2
default_subagent_model = "gpt-6-luna"
default_subagent_reasoning_effort = "medium"
```

Профиль является источником рекомендуемых значений, а не файлом для слепой замены локального `~/.codex/config.toml`.

Перед применением на каждой машине необходимо:

1. проверить версию Codex;
2. проверить доступность указанных моделей и ключей конфигурации;
3. сравнить только управляемые ключи;
4. показать diff;
5. сохранить все остальные локальные настройки;
6. применить значения после подтверждения;
7. проверить фактическую загрузку конфигурации.

Если конкретная версия не поддерживает значение, синхронизация ничего не подменяет автоматически и запрашивает решение пользователя.

### 4.4. Инструкция для обычного ChatGPT

`memory/USAGE_OPTIMIZATION.md` содержит короткий канонический блок для Custom Instructions или Project Instructions ChatGPT:

```text
Перед ответом молча оцени, подходит ли для задачи ChatGPT, Codex или
детерминированный инструмент, и достаточна ли текущая модель и скорость.
Если выбранный режим существенно избыточен или неподходящ, сообщи об этом
одной короткой фразой и предложи конкретную альтернативу. В остальных
случаях сразу отвечай. Не дублируй работу, уже выполненную в Codex:
используй краткий handoff с решением, критериями и результатами проверок.
```

Инструкция применяется один раз на уровне общей учётной записи или нужного ChatGPT Project после проверки фактической области действия. Она не синхронизируется через локальный Codex `AGENTS.md`.

## 5. Resource preflight

Preflight выполняется внутренне и не должен создавать самостоятельный длинный ответ.

Codex определяет:

1. Нужен ли LLM или задача детерминирована.
2. Подходит ли ChatGPT, Codex, CLI, специализированный коннектор либо browser/computer use.
3. Какой минимальный класс модели достаточен.
4. Какой reasoning effort достаточен.
5. Требуется ли fast mode.
6. Требуется ли делегирование и являются ли ветви действительно независимыми.
7. Нужны ли актуальные сведения о текущем лимите.
8. Требуются ли бюджет, лимит попыток и STOP-условие.

### 5.1. Нормальное поведение

Если текущий режим подходит, Codex сразу выполняет задачу. Пользователь не получает формальный отчёт о preflight.

### 5.2. Существенное несоответствие

Перед дорогой работой Codex выводит не более одной короткой рекомендации:

```text
Оптимизация: эту задачу выгоднее выполнить в Codex на Luna medium без fast mode и без субагентов.
```

Предупреждение не блокирует тривиальную безопасную задачу. Если изменение требует выбора пользователя или невозможно применить внутри текущей сессии, Codex запрашивает решение до существенного расхода.

### 5.3. Явный выбор пользователя

Явно выбранные модель, reasoning, speed или способ выполнения не меняются молча. Codex может один раз предупредить о существенном перерасходе и предложить альтернативу, но прямой допустимый выбор пользователя сохраняется.

## 6. Матрица сложности

| Класс | Характер работы | Базовый маршрут |
|---|---|---|
| D | Бэкап, сортировка, точное сравнение, тест, хеширование, расписание | Код/CLI/Task Scheduler/CI без LLM |
| S | Короткая чёткая операция, извлечение, форматирование, небольшой файл | Лёгкая модель, low/medium, один агент |
| M | Обычная разработка, диагностика, исследование с проверкой | Рабочая модель, medium, один агент |
| L | Неоднозначная архитектура, сложный межсистемный анализ | Рабочая high или старшая medium; до двух независимых субагентов |
| C | Критический аудит или решение с высокой ценой ошибки | Сильная модель и отдельная проверка по явным критериям |

Переход к более сильному режиму выполняется по наблюдаемой сложности или провалу проверенной гипотезы, а не автоматически после любого неудачного ответа.

## 7. Бюджетная политика

Ориентиры являются эвристикой, а не гарантией:

| Использовано недельного лимита | Режим |
|---:|---|
| 0–50% | Обычная маршрутизация D/S/M/L/C |
| 50–70% | Простые задачи — лёгкая модель; старшая модель только с обоснованием |
| 70–85% | Завершение начатого; без новых широких исследований, fast mode и веера агентов |
| >85% | Только критичная работа; по возможности детерминированные инструменты |

Текущий расход проверяется перед потенциально дорогой задачей, по запросу пользователя или после достижения известного порога. Проверка не выполняется перед каждым простым сообщением.

## 8. Синхронизация

`SYNC.md` расширяется отдельной фазой конфигурационного профиля после интеграции managed-блока `AGENTS.md`:

```text
fetch → diff → classify → review → managed AGENTS integration
      → usage profile compatibility check → config diff → approval
      → config integration → verification → report
```

Конфигурационный профиль и managed-блок имеют независимые approval gates. Принятие обновления инструкций не означает автоматического изменения `config.toml`.

Отчёт синхронизации дополнительно перечисляет:

- поддерживается ли рекомендуемый профиль;
- прежние и новые значения управляемых ключей;
- сохранённые локальные настройки;
- несовместимые или отложенные значения;
- результат проверки модели, reasoning, service tier и ограничения агентов.

## 9. Изменяемые файлы реализации

После утверждения спецификации план реализации должен охватывать:

- `AGENTS_CORE.md` — короткий активный раздел;
- `memory/USAGE_OPTIMIZATION.md` — подробная политика;
- `config/USAGE_PROFILE.toml` — канонический рекомендуемый профиль;
- `SYNC.md` — безопасное сравнение и применение профиля;
- `README.md` — описание новой архитектурной части;
- `CHANGELOG.md` — существенное изменение поведения;
- `VERSION` — minor version bump;
- тесты или проверяющий скрипт для структуры профиля и обязательных разделов.

Глобальный `~/.codex/AGENTS.md` и локальный `~/.codex/config.toml` не изменяются на этапе подготовки репозитория. Их интеграция выполняется отдельным подтверждённым шагом после проверки diff.

## 10. Проверка реализации

Минимальные проверки:

1. Managed-маркеры `AGENTS_CORE.md` существуют ровно по одному разу и имеют правильный порядок.
2. Активное ядро остаётся коротким и не содержит привязки к текущим названиям моделей.
3. TOML-профиль синтаксически корректен и содержит только разрешённые общие ключи.
4. `SYNC.md` запрещает полную замену локального `config.toml`.
5. Metadata в справочной политике соответствует `memory/VALIDITY.md`.
6. Все внешние изменчивые утверждения имеют актуальные первичные источники.
7. Ссылки открываются, текст читается как UTF-8, секреты отсутствуют.
8. Итоговый diff не затрагивает `LOCAL OVERRIDES`, проектные репозитории или локальные MCP/permissions.
9. На текущей машине после отдельного approval выполняется smoke test загрузки модели, reasoning, service tier и ограничения субагентов.
10. На остальных машинах применяется процедура `fetch → diff → classify → review → integration → report`.

## 12. Вне области этой реализации

- Покупка дополнительной подписки или API-бюджета.
- Автоматическое использование reset credits.
- Полная унификация MCP, плагинов, разрешений, путей или уведомлений между машинами.
- Автоматическая смена явно выбранной пользователем модели.
- Создание обязательного skill, загружаемого перед каждой задачей.
- Публикация в GitHub до review итогового diff и отдельного подтверждения пользователя.

## 13. Риски и защита

- **Устаревание моделей:** активное ядро использует роли; конкретные модели хранятся в `verify-current` справочнике и профиле.
- **Лишняя церемония:** preflight молчаливый; предупреждение появляется только при существенном несоответствии.
- **Потеря качества от слишком слабой модели:** эскалация разрешена по наблюдаемой сложности и результатам проверки.
- **Повреждение локальной конфигурации:** применяется allowlist ключей, независимый diff и approval; полный файл не заменяется.
- **Различия версий:** профиль сначала проходит compatibility check на каждой установке.
- **Разрастание контекста:** подробный файл читается по релевантности, а не на каждом ходе.

## 14. Критерии готовности

Реализация готова, когда:

1. все файлы из раздела 9 изменены и проверены;
2. тесты структуры и профиля проходят;
3. пользователь просмотрел итоговый diff репозитория;
4. изменения опубликованы только после явного подтверждения;
5. текущая машина интегрирована и проверена отдельно;
6. две другие машины получили одинаковое ядро и совместимый профиль с сохранёнными локальными настройками;
7. двухнедельный контроль показывает направление к диапазону 80–85% без планового reset.

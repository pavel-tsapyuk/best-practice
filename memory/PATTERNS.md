# Reusable Patterns

```yaml
scope: shared
stability: heuristic
conflict: ask
```

Паттерны являются кандидатами для повторного использования, а не обязательными шаблонами. Перед применением проверь соответствие задаче.

## 1. Проверка PDF/макета по эталонной таблице

Pipeline:
1. PDF → изображения страниц.
2. Vision model → извлечение визуального содержимого.
3. Нормализация значений.
4. Fuzzy matching, например RapidFuzz.
5. Строгое сравнение обычным кодом.
6. HTML/табличный отчёт о расхождениях.

Применение:
- коммерческие предложения;
- прайсы;
- спецификации;
- документы клиента;
- макеты;
- сверка PDF с Excel/1С/CRM.

Принцип: модель понимает неструктурированный/визуальный контекст, классический код выполняет точные проверки.

## 2. Встреча → КП / ТЗ

Pipeline:
1. запись встречи;
2. транскрипция;
3. извлечение требований;
4. нормализация требований;
5. сопоставление с типовыми работами;
6. выявление рисков и неясностей;
7. черновик состава работ/ТЗ;
8. предварительная оценка;
9. автоматические проверки;
10. human approval.

## 3. Большое исследование / руководство

Pipeline:
1. сбор источников;
2. фильтрация и ранжирование;
3. проектирование структуры;
4. извлечение материала;
5. сборка;
6. редактура;
7. проверка ссылок/фактов;
8. человеческое утверждение.

## 4. Двухуровневый глоссарий

Для больших переводных/двуязычных документов:
1. новый термин попадает в список кандидатов;
2. человек или проверяющий процесс утверждает перевод;
3. термин становится каноническим;
4. последующие этапы обязаны использовать каноническую форму.

Применение:
- RU/EN договоры;
- ТЗ;
- длинная техническая документация.

## 5. Evaluator / Optimizer

1. Генератор создаёт результат.
2. Отдельный evaluator оценивает его по явным критериям.
3. При несоответствии результат возвращается на исправление.
4. Цикл ограничен числом попыток и STOP-условиями.

Не использовать, если простая однократная проверка обычным кодом надёжнее.

## 6. Узкая автоматизация до агента

Перед проектированием агента проверить:
1. можно ли решить задачу обычным кодом;
2. можно ли решить workflow;
3. достаточно ли одного LLM-вызова;
4. нужен ли выбор инструментов/планирование;
5. существует ли измеримый ROI.

Только после этого переходить к агентности.

## 7. Лестница сложности памяти агента

Не начинать с векторной или графовой базы без подтверждённой необходимости:

1. Сначала хранить небольшую память в обычном тексте с явными заголовками, источниками и датами.
2. Перейти к SQLite, когда нужны атомарные обновления, фильтры, история и устойчивые идентификаторы.
3. Начать поиск с детерминированных фильтров и ключевых слов.
4. Добавлять embeddings/RAG только после измеримого провала простого поиска на реальных запросах.
5. Добавлять граф только для задач, где связи, происхождение решений или временная структура действительно являются предметом запросов.
6. Разделять относительно статичные ресурсы, динамическую память и исполняемые skills.
7. Хранить происхождение записи, состояние `active/retired`, дату проверки и способ удаления.
8. Не повышать автоматически извлечённую память до общего правила без человеческого review.

## 8. Минимальный agent harness

Строить обвязку причинно: добавлять компонент после того, как реальный сбой доказал его необходимость.

Минимальные слои зрелого harness:

1. ограниченный tool loop со STOP-условиями;
2. узкие инструменты с явными контрактами входа, выхода и запретами;
3. проверки прав и approval gates перед побочными эффектами;
4. сменяемая среда выполнения/песочница за единым интерфейсом;
5. ограничение размеров чтения и вывода, pruning устаревших результатов;
6. изоляция контекста и прав при делегировании;
7. явный канал `ask user` для существенной неоднозначности;
8. управляемый жизненный цикл, снимки и восстановление для долгих задач;
9. skills с progressive disclosure;
10. обязательная проверка результата, а не доверие к текстовому заявлению агента.

Если нужны воспроизводимость, аудит или восстановление после сбоя, хранить сообщения модели, tool calls, решения по разрешениям и завершения как append-only события. UI, следующий prompt и восстановленное состояние строить как проекции журнала, а не делать их единственной копией данных. Архитектурный пример — [Apache Maka](https://github.com/apache/maka); сам проект остаётся изменчивым кандидатом, а не обязательной зависимостью.

Справочник для изучения конструкции: [Build Your Own AI Coding Agent Harness](https://vercel.com/academy/build-ai-agent-harness).

## 9. Визуальный замкнутый цикл

Для UI, игр, документов и других визуальных результатов:

1. выполнить изменение;
2. получить свежий render/screenshot фактического результата;
3. сравнить его с явными критериями или эталоном;
4. локализовать расхождение;
5. исправить одну причину;
6. повторить цикл с новым снимком;
7. остановиться по criteria of done или лимиту попыток.

Дополнять визуальную оценку детерминированными проверками: тестами, схемами, размерами, доступностью и анализом ошибок. Практический пример такого цикла — [Godogen](https://github.com/htdt/godogen).

## 10. A/B-проверка skill или plugin

1. Собрать небольшой набор реальных пользовательских запросов, включая случаи, где skill должен и не должен срабатывать.
2. Для каждого запроса определить наблюдаемые критерии результата и, при необходимости, допустимый порядок инструментов.
3. Выполнить несколько изолированных прогонов с расширением и без него.
4. Сравнить качество, стоимость, время, число действий и стабильность результата.
5. Не считать высокий абсолютный результат доказательством пользы: важна разница относительно baseline без расширения.
6. Hooks, MCP и scripts запускать только из доверенного расширения и с минимальными правами.
7. Если расширение не даёт измеримого выигрыша, сузить его trigger/инструкции или удалить.

Практическая реализация этого подхода для Claude Code описана в [plugin evals](https://code.claude.com/docs/en/plugin-evals); общий принцип применим и к Codex skills.

## 11. Человек-автор, агенты-исследователи

Для авторского контента разделять работу:

1. агенты мониторят источники, транскрибируют, собирают фактуру, выявляют повторы и готовят вопросы для проверки;
2. факты подтверждаются первичными источниками;
3. человек определяет тезис, позицию, структуру и финальную формулировку;
4. перед публикацией человек проверяет факты, ссылки, тон и возможный вред.

Не превращать этот паттерн в полностью автоматический контент-завод: его цель — снять механическую работу, сохранив авторскую и редакционную ответственность.

## 12. Локальный захват и отложенная обработка аудио

```yaml
scope: project
stability: project-specific
conflict: preserve-local
```

Если разговоры нельзя без необходимости отправлять внешнему сервису:

1. сохранять исходное аудио локально;
2. выполнять распознавание локальной моделью, когда оборудование это позволяет;
3. при отсутствии сети буферизовать записи и обрабатывать их позже;
4. передавать в базу знаний только необходимые данные с явным сроком хранения;
5. отдельно определить согласие участников, правила удаления и доступ к транскриптам.

Конкретные устройства и модели выбираются локально; паттерн не требует ESP32, Parakeet или определённой базы знаний.

## 13. Стабильный префикс и измеряемый effort в LLM API

```yaml
scope: project
stability: verify-current
conflict: ask
```

Для API-процессов с prompt caching:

1. располагать стабильные определения tools, системные инструкции и повторно используемый контекст до изменчивых данных;
2. помещать timestamps, request IDs, текущий статус и пользовательский ввод после кэшируемого префикса;
3. не менять порядок tools между одинаковыми запросами без необходимости;
4. измерять cache hit rate, стоимость успешного результата и задержку;
5. подбирать effort экспериментом: максимальное значение не считать автоматически лучшим.

Перед реализацией сверять механику с документацией конкретного провайдера. Для Claude: [prompt caching](https://platform.claude.com/docs/en/build-with-claude/prompt-caching) и [cost/intelligence optimization](https://platform.claude.com/docs/en/about-claude/models/optimizing-for-cost-and-intelligence).

## 14. Ограниченная маршрутизация на дешёвую модель

```yaml
scope: project
stability: heuristic
conflict: ask
```

Более дешёвую модель можно экспериментально использовать для:

- первичного обзора очень больших файлов с краткой выборкой релевантных фрагментов;
- повторяющегося кода по строгому образцу;
- механической нормализации данных.

Не делегировать ей debugging, архитектурные решения, безопасность и критические изменения. Основная модель должна читать конкретные изменяемые фрагменты, а итог обязан пройти обычные тесты и review. Не вводить жёсткий порог размера файла глобально: сначала измерить качество, latency и экономию на реальном проекте. Источник эксперимента — [Spotify Engineering](https://engineering.atspotify.com/2026/9/portal-by-spotify-cut-my-claude-code-token-usage-by-90).

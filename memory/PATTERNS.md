# Reusable Patterns

```yaml
scope: shared
stability: heuristic
conflict: ask
```

Паттерны являются кандидатами для повторного использования, а не обязательными шаблонами. Перед применением проверь соответствие задаче.

## 1. Проверка PDF/макета по эталонной таблице

Pipeline:
1. PDF → изображения страниц.
2. Vision model → извлечение визуального содержимого.
3. Нормализация значений.
4. Fuzzy matching, например RapidFuzz.
5. Строгое сравнение обычным кодом.
6. HTML/табличный отчёт о расхождениях.

Применение:
- коммерческие предложения;
- прайсы;
- спецификации;
- документы клиента;
- макеты;
- сверка PDF с Excel/1С/CRM.

Принцип: модель понимает неструктурированный/визуальный контекст, классический код выполняет точные проверки.

## 2. Встреча → КП / ТЗ

Pipeline:
1. запись встречи;
2. транскрипция;
3. извлечение требований;
4. нормализация требований;
5. сопоставление с типовыми работами;
6. выявление рисков и неясностей;
7. черновик состава работ/ТЗ;
8. предварительная оценка;
9. автоматические проверки;
10. human approval.

## 3. Большое исследование / руководство

Pipeline:
1. сбор источников;
2. фильтрация и ранжирование;
3. проектирование структуры;
4. извлечение материала;
5. сборка;
6. редактура;
7. проверка ссылок/фактов;
8. человеческое утверждение.

## 4. Двухуровневый глоссарий

Для больших переводных/двуязычных документов:
1. новый термин попадает в список кандидатов;
2. человек или проверяющий процесс утверждает перевод;
3. термин становится каноническим;
4. последующие этапы обязаны использовать каноническую форму.

Применение:
- RU/EN договоры;
- ТЗ;
- длинная техническая документация.

## 5. Evaluator / Optimizer

1. Генератор создаёт результат.
2. Отдельный evaluator оценивает его по явным критериям.
3. При несоответствии результат возвращается на исправление.
4. Цикл ограничен числом попыток и STOP-условиями.

Не использовать, если простая однократная проверка обычным кодом надёжнее.

## 6. Узкая автоматизация до агента

Перед проектированием агента проверить:
1. можно ли решить задачу обычным кодом;
2. можно ли решить workflow;
3. достаточно ли одного LLM-вызова;
4. нужен ли выбор инструментов/планирование;
5. существует ли измеримый ROI.

Только после этого переходить к агентности.

## 7. Лестница сложности памяти агента

Не начинать с векторной или графовой базы без подтверждённой необходимости:

1. Сначала хранить небольшую память в обычном тексте с явными заголовками, источниками и датами.
2. Перейти к SQLite, когда нужны атомарные обновления, фильтры, история и устойчивые идентификаторы.
3. Начать поиск с детерминированных фильтров и ключевых слов.
4. Добавлять embeddings/RAG только после измеримого провала простого поиска на реальных запросах.
5. Добавлять граф только для задач, где связи, происхождение решений или временная структура действительно являются предметом запросов.
6. Разделять относительно статичные ресурсы, динамическую память и исполняемые skills.
7. Хранить происхождение записи, состояние `active/retired`, дату проверки и способ удаления.
8. Не повышать автоматически извлечённую память до общего правила без человеческого review.

## 8. Минимальный agent harness

Строить обвязку причинно: добавлять компонент после того, как реальный сбой доказал его необходимость.

Минимальные слои зрелого harness:

1. ограниченный tool loop со STOP-условиями;
2. узкие инструменты с явными контрактами входа, выхода и запретами;
3. проверки прав и approval gates перед побочными эффектами;
4. сменяемая среда выполнения/песочница за единым интерфейсом;
5. ограничение размеров чтения и вывода, pruning устаревших результатов;
6. изоляция контекста и прав при делегировании;
7. явный канал `ask user` для существенной неоднозначности;
8. управляемый жизненный цикл, снимки и восстановление для долгих задач;
9. skills с progressive disclosure;
10. обязательная проверка результата, а не доверие к текстовому заявлению агента.

Справочник для изучения конструкции: [Build Your Own AI Coding Agent Harness](https://vercel.com/academy/build-ai-agent-harness).

## 9. Визуальный замкнутый цикл

Для UI, игр, документов и других визуальных результатов:

1. выполнить изменение;
2. получить свежий render/screenshot фактического результата;
3. сравнить его с явными критериями или эталоном;
4. локализовать расхождение;
5. исправить одну причину;
6. повторить цикл с новым снимком;
7. остановиться по criteria of done или лимиту попыток.

Дополнять визуальную оценку детерминированными проверками: тестами, схемами, размерами, доступностью и анализом ошибок. Практический пример такого цикла — [Godogen](https://github.com/htdt/godogen).

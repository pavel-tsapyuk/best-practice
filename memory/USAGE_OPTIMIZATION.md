# Оптимизация использования ChatGPT и Codex

Проверено по официальной документации OpenAI: 2026-09-24.

Этот документ раскрывает короткое активное правило из `AGENTS_CORE.md`.
Читайте только относящиеся к текущей задаче разделы: полная загрузка файла
перед каждой простой операцией сама противоречит цели экономии контекста.

## Устойчивые правила

```yaml
scope: shared
stability: stable
conflict: enforce-shared
```

Перед каждой задачей молча определи, нужен ли LLM, какой инструмент подходит
и какие минимальные модель, reasoning, скорость и число агентов достаточны.
Если задачу надёжно решает обычный код, CLI, тест или расписание, предпочти
детерминированный маршрут.

Если текущий режим подходит, сразу выполняй задачу без формального отчёта о
preflight. Если режим существенно избыточен, перед дорогой работой дай не
более одной короткой рекомендации с конкретной альтернативой. Явный выбор
пользователя не меняй молча.

Для долгой задачи до исполнения определи criteria of done, максимум две
попытки одной гипотезы, STOP-условие и краткий формат результата. Завершение
подтверждай фактической проверкой, а не заявлением модели.

Повышай сложность только по наблюдаемой необходимости: доказанной
неоднозначности, провалу проверенной гипотезы, высокой цене ошибки или
независимым ветвям работы. Не повышай reasoning и не создавай субагентов
автоматически после любого неудачного ответа.

## Матрица D/S/M/L/C

```yaml
scope: shared
stability: heuristic
conflict: ask
```

| Класс | Работа | Маршрут |
|---|---|---|
| D | Бэкап, сортировка, точное сравнение, тест, хеширование, расписание | Код/CLI/Task Scheduler/CI без LLM |
| S | Короткая чёткая операция, извлечение, форматирование, небольшой файл | Лёгкая модель, low/medium, один агент |
| M | Обычная разработка, диагностика, исследование с проверкой | Рабочая модель, medium, один агент |
| L | Неоднозначная архитектура, сложный межсистемный анализ | Рабочая high или старшая medium; до двух независимых субагентов |
| C | Критический аудит или высокая цена ошибки | Сильная модель и отдельная проверка по явным критериям |

Класс — это рабочая гипотеза, а не постоянная метка проекта. Большой проект
может состоять из множества D/S/M-операций и одной L-задачи.

## ChatGPT, Codex или детерминированный инструмент

```yaml
scope: shared
stability: stable
conflict: enforce-shared
```

- ChatGPT формулирует задачу, сравнивает варианты, объясняет незнакомую тему
  и помогает принять решение.
- Codex читает фактические файлы и состояние среды, вносит изменения,
  запускает проверки и создаёт проверяемый артефакт.
- Обычный код, CLI, тест, планировщик или CI выполняет точную повторяемую
  операцию без рассуждения.

Не исследуй одну проблему полностью в ChatGPT, а затем заново в Codex.
Передача ChatGPT → Codex должна содержать выбранное решение, criteria of
done, ограничения и ссылки на входные файлы, а не полный разговор. После
работы Codex передавай в ChatGPT только итоговый diff, результаты проверок
и конкретный вопрос.

## Модели и reasoning

```yaml
scope: local-default
stability: verify-current
conflict: preserve-local
```

| Класс задачи | Модель | Reasoning |
|---|---|---|
| S | GPT-6 Luna | low/medium |
| M | GPT-6 Sol | medium |
| L | GPT-6 Sol high или GPT-6 Astra medium | high/medium |
| C | GPT-6 Astra или GPT-6 Sol с отдельной проверкой | high |

Перед применением проверь актуальную документацию, доступность модели и
поддерживаемые уровни reasoning на конкретной установке.

Начинай с минимального режима, который правдоподобно выполнит criteria of
done. High нужен для сложной логики, проверки предположений и существенных
edge cases. Xhigh/max/ultra допустимы только для узкой доказанно трудной
части, а не как общий режим сессии.

Если явно выбранная пользователем модель избыточна, предупреди один раз до
дорогой работы и предложи точную альтернативу. Не меняй выбор молча.

## Скорость

```yaml
scope: local-default
stability: verify-current
conflict: preserve-local
```

`default` является нормальным service tier. Fast mode допустим только когда
выигрыш времени важнее повышенного расхода и пользователь сделал осознанный
выбор. Перед применением проверь актуальную стоимость режима по официальной
документации и фактическое состояние на установке.

## Субагенты

```yaml
scope: shared
stability: stable
conflict: enforce-shared
```

Один агент — режим по умолчанию. Параллельно работают не более двух
субагентов, если более конкретная утверждённая конфигурация проекта не
требует иного. Каждая ветвь должна быть действительно независимой и иметь
узкий контракт результата.

Не делегируй одиночный поиск, чтение файла, простую проверку, форматирование
или точную операцию, которую надёжнее выполнит код. Для лёгких обзоров и
поиска используй лёгкую модель; сильную модель назначай только ветви, где
нужна её способность. Вложенное размножение агентов запрещено без явного
обоснования и пользовательского решения.

## Browser, Computer Use и MCP

```yaml
scope: shared
stability: heuristic
conflict: ask
```

Предпочитай специализированный коннектор, API, CLI или чтение локального
файла. Browser и Computer Use используй, когда семантического интерфейса нет
или задача требует фактического взаимодействия с UI.

Пакетируй независимые чтения и поиски, ограничивай результат нужными полями,
не возвращай полный DOM или длинный лог без необходимости. Отключай
нерелевантные MCP-инструменты на уровне проекта и прекращай инструментальный
цикл сразу после получения проверяемого результата.

## Управление контекстом

```yaml
scope: shared
stability: stable
conflict: enforce-shared
```

- Одна устойчивая цель соответствует одной задаче.
- `/side` используется для бокового вопроса, который не должен менять
  основной контекст.
- `/compact` используется после завершённого этапа той же цели, когда
  история разрослась логами и промежуточными результатами.
- Новая задача или fork используется при смене цели.
- Между компьютерами передавай Git commit/diff и короткий handoff: цель,
  текущее состояние, проверки, следующая команда и блокеры.
- Не переноси полный разговор, если достаточно проверенного результата.

## Недельные пороги

```yaml
scope: shared
stability: heuristic
conflict: ask
```

| Использовано недельного лимита | Режим |
|---:|---|
| 0–50% | Обычная маршрутизация D/S/M/L/C |
| 50–70% | Простые задачи — лёгкая модель; старшая модель только с обоснованием |
| 70–85% | Завершение начатого; без новых широких исследований, fast mode и веера агентов |
| >85% | Только критичная работа; по возможности детерминированные инструменты |

Проверяй текущий расход перед потенциально дорогой задачей, по запросу
пользователя или после достижения известного порога. Не вызывай проверку
лимита перед каждым простым сообщением.

Целевой недельный диапазон 80–85% является ориентиром этой установки, а не
универсальной гарантией. Корректируй его только по статистике одинаковых
полных окон и качеству проверенных результатов.

## Инструкция для ChatGPT

```yaml
scope: local-default
stability: stable
conflict: preserve-local
```

Канонический блок для ChatGPT Custom Instructions или Project Instructions:

```text
Перед ответом молча оцени, подходит ли для задачи ChatGPT, Codex или
детерминированный инструмент, и достаточна ли текущая модель и скорость.
Если выбранный режим существенно избыточен или неподходящ, сообщи об этом
одной короткой фразой и предложи конкретную альтернативу. В остальных
случаях сразу отвечай. Не дублируй работу, уже выполненную в Codex:
используй краткий handoff с решением, критериями и результатами проверок.
```

Перед добавлением проверь фактическую область действия инструкции. Не
дублируй её на каждом компьютере, если настройка уже применяется ко всей
учётной записи.

## Аудит

```yaml
scope: shared
stability: heuristic
conflict: ask
```

Для крупных задач записывай минимум:

```text
date | machine | task class | tool | model | reasoning | speed |
subagents | repair rounds | verified outcome
```

Сравнивай одинаковую точку двух последовательных недельных окон. Анализируй
пять задач с наибольшим числом субагентов, repair rounds или дорогих режимов.
Не считай сообщения, команды или токены самостоятельным результатом:
основная метрика — проверенная полезная работа без ручной переделки.

Если расход остаётся выше 85%, меняй один контроль за раз: сначала число
субагентов, затем маршрутизацию S-задач, reasoning или детерминированные
автоматизации. Одновременная смена всех параметров не позволит определить,
что именно сработало.
